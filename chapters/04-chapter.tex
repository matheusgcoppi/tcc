\chapter{RESULTADOS E ANÁLISE} \label{cap:resultados}
% ----------------------------------------------------------

Para avaliar empiricamente as diferenças entre REST e gRPC, foi desenvolvido o script \texttt{compare\_full.sh} que automatiza a execução de testes comparativos. O script realiza requisições para o endpoint \texttt{/certificate/all} no servidor REST e para o método RPC \texttt{GetAllCertificates} no servidor gRPC, ambos retornando o conjunto completo de certificados armazenados.

Os testes foram executados com duas bases distintas de certificados para avaliar o comportamento dos protocolos em diferentes escalas. O primeiro teste utilizou 5.110 certificados (aproximadamente 6,4 MB) e o segundo utilizou 15.110 certificados (aproximadamente 19 MB). O \textit{script} mede três aspectos principais: tamanho do \textit{payload} transmitido, tempo de transferência completa e calcula métricas derivadas como redução de tamanho, fator de \textit{speedup} e economia de largura de banda em cenários de múltiplas requisições.

% ----------------------------------------------------------
\section{METODOLOGIA DE EXECUÇÃO DOS TESTES}\label{sec:metodologia-testes}
% ----------------------------------------------------------

O script \texttt{compare\_full.sh} implementa a metodologia de teste completa. Para o servidor REST, o script utiliza \texttt{curl} para requisitar o endpoint \texttt{/certificate/all}, salva a resposta JSON em arquivo temporário, e mede o tempo total usando \texttt{date +\%s.\%N} antes e depois da requisição. O comando \texttt{wc -c} extrai o tamanho do arquivo em bytes, e \texttt{jq '.|length'} conta o número de certificados no JSON retornado.

Para o servidor gRPC, o \textit{script} compila dinamicamente um cliente Go temporário que importa o \textit{package} \texttt{proto} gerado, conecta ao servidor na porta 50051, invoca \texttt{GetAllCertificates}, e serializa a resposta completa usando \texttt{proto.Marshal} para obter o tamanho binário exato do \textit{payload Protobuf}. Este cliente também mede o tempo de transferência completa. A compilação em tempo de execução permite que o \textit{script} seja executado sem dependências pré-compiladas.

O \textit{script} calcula automaticamente três métricas principais: redução de tamanho (percentual e absoluto), fator de \textit{speedup} (razão entre tempos de REST e gRPC), e economia de largura de banda projetada para 100 requisições. Os resultados são formatados em tabela ASCII e salvos em arquivo de \textit{log} com \textit{timestamp}. Esta automação permitiu executar múltiplas iterações dos testes para validar a consistência dos resultados.

Os certificados utilizados nos testes foram gerados previamente usando o \textit{endpoint} \texttt{POST /certificate} do servidor REST. Cada certificado contém \textit{Subject} padrão (\textit{CommonName}="localhost", \textit{Organization}="Test"), validade de 1 ano, e \textit{payload} JSON vazio. Os arquivos foram armazenados em \texttt{zarf/certificates/} com nomenclatura \texttt{certificate\_YYYYMMDD\_HHMMSS\_nnnnnnnnn.crt}, onde os nanosegundos garantem unicidade. Este formato PEM padrão ocupa aproximadamente 1,3 KB por certificado.

Entre cada teste, os servidores foram reiniciados usando \texttt{docker-compose restart rest-app grpc-app} para limpar caches de memória e garantir condições iniciais equivalentes. Após a reinicialização, aguardou-se 10 segundos para estabilização completa dos processos antes de executar as requisições de teste. Esta metodologia elimina variáveis de estado residual que poderiam influenciar os resultados.

\subsection{Análise do Tamanho de Payload}

Nos testes executados, foram observados os seguintes tamanhos de payload:

**Teste com 5.110 certificados:**
\begin{itemize}
    \item REST/JSON: 6.750.564 bytes (6,43 MB)
    \item gRPC/Protobuf: 6.653.472 bytes (6,35 MB)
    \item Redução: 97.092 bytes (2\%)
\end{itemize}

**Teste com 15.110 certificados:**
\begin{itemize}
    \item REST/JSON: 19.960.564 bytes (19,03 MB)
    \item gRPC/Protobuf: 19.673.472 bytes (18,76 MB)
    \item Redução: 287.092 bytes (2\%)
\end{itemize}

A redução de payload manteve-se consistente em 2\% em ambos os testes, independentemente da escala (5k ou 15k certificados).

\subsection{Análise do Tempo de Transferência}

Nos testes de tempo de transferência, foram observados:

**Teste com 5.110 certificados:**
\begin{itemize}
    \item REST: 1,985 segundos
    \item gRPC: 0,657 segundos
    \item Speedup: 3,02x (gRPC 3 vezes mais rápido)
    \item Diferença absoluta: 1,328 segundos
\end{itemize}

**Teste com 15.110 certificados:**
\begin{itemize}
    \item REST: 3,438 segundos
    \item gRPC: 1,944 segundos
    \item Speedup: 1,76x (gRPC 76\% mais rápido)
    \item Diferença absoluta: 1,494 segundos
\end{itemize}

O speedup foi mais pronunciado no teste de 5k certificados (3,02x) comparado ao teste de 15k certificados (1,76x). A diferença absoluta de tempo manteve-se próxima em ambos os cenários (~1,4-1,5 segundos).

\subsection{Projeção de Economia de Largura de Banda}

O script calcula projeções para cenários de múltiplas requisições. No teste com 5.110 certificados, 100 requisições consumiriam 643 MB com REST e 634,52 MB com gRPC, economizando 8,48 MB. No teste com 15.110 certificados, 100 requisições totalizariam 1.903 MB com REST e 1.876,21 MB com gRPC, economizando 26,79 MB.

A economia proporcional se mantém constante em 2\%, mas o volume absoluto economizado escala linearmente com o tamanho dos dados. Em sistemas de alta escala com milhões de requisições diárias, essa diferença se torna significativa. Considerando o cenário maior, 1 milhão de requisições economizaria aproximadamente 268 GB de tráfego de rede, reduzindo custos de transferência em ambientes cloud que cobram por largura de banda.

Além da economia financeira, a redução de largura de banda beneficia usuários em redes com capacidade limitada ou tarifadas por volume de dados, como conexões móveis. O tempo total economizado em 1 milhão de requisições no cenário de 15.110 certificados seria de aproximadamente 415 horas (17 dias) considerando o speedup de 1,76x, representando ganho substancial de eficiência operacional.

\section{ANÁLISE DE CONSUMO DE RECURSOS}\label{sec:consumo-recursos}
% ----------------------------------------------------------

As métricas de CPU e memória foram coletadas pelo cAdvisor com resolução de 1 segundo e armazenadas no Prometheus. Foram realizados testes com dois volumes de dados: 15.110 certificados (19 MB) e 5.000 certificados (6,4 MB).

\subsection{Resultados do Teste com 15.110 Certificados}

As Figuras \ref{fig:grafana-rest} e \ref{fig:grafana-grpc} apresentam as métricas coletadas durante a transferência de 15.110 certificados. Os gráficos exibem o consumo de CPU em percentual e o uso de memória em mebibytes (MiB) ao longo de todo o período de execução do teste, capturando tanto o momento da requisição quanto o período de estabilização posterior.

As métricas foram visualizadas através de \textit{dashboards} personalizados criados no \textit{Grafana}. Foram configuradas \textit{queries} PromQL específicas para extrair as métricas do \textit{cAdvisor}: \texttt{container\_cpu\_usage\_seconds\_total} para utilização de CPU normalizada por número de cores, e \texttt{container\_memory\_working\_set\_bytes} para consumo de memória RSS excluindo cache. Os gráficos foram configurados com janela de tempo sincronizada para permitir comparação visual direta entre os servidores.

Durante a execução dos testes, o \textit{Grafana} foi mantido aberto em modo de atualização automática (\textit{refresh} de 5 segundos) para observar o comportamento em tempo real. Foi executado o comando \texttt{curl http://localhost:8000/certificate/all} para REST e o cliente gRPC equivalente, observando-se os picos de recursos no momento exato da transferência. Os gráficos capturados nas figuras representam uma janela temporal de aproximadamente 10 minutos, incluindo o período antes, durante e após a requisição.

Os servidores estavam em estado \textit{idle} antes de cada teste, com consumo de CPU próximo a zero e memória base (\textit{footprint} do processo Go e suas estruturas). Após a requisição, foi observado o pico de utilização durante o processamento, seguido de declínio gradual à medida que o \textit{garbage collector} do Go liberava memória não utilizada. O período de estabilização completo levou cerca de 2-3 minutos em ambos os servidores.

Para garantir captura precisa dos picos, foi sincronizada manualmente a execução do comando \texttt{curl} com a observação do \textit{timestamp} no \textit{Grafana}. Aguardou-se o servidor estabilizar completamente (CPU < 0,1\% por pelo menos 30 segundos) antes de executar cada requisição de teste. Após a execução, aguardou-se o consumo de memória retornar a valores próximos ao \textit{baseline} antes de capturar o \textit{screenshot}. Esta metodologia assegurou que os gráficos capturassem o ciclo completo de carga-processamento-estabilização.

Os \textit{screenshots} foram salvos em resolução 1920x1080 diretamente do navegador \textit{Chrome} em tela cheia, com \textit{zoom} de 100\% para garantir legibilidade dos valores numéricos nas legendas. As imagens foram editadas apenas para recortar bordas desnecessárias do navegador, mantendo toda a área de gráficos intacta.
