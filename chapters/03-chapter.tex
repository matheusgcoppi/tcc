\section{VISÃO GERAL DO PROJETO}\label{sec:visao}
% ----------------------------------------------------------

O projeto consiste em uma implementação prática para comparar os protocolos REST e gRPC em uma arquitetura de microsserviços. A aplicação foi desenvolvida em Go e possui dois servidores independentes: um utilizando REST com JSON e outro usando gRPC com Protocol Buffers. Ambos compartilham a mesma lógica de negócio para garantir uma comparação justa.

A funcionalidade implementada envolve a geração de certificados X.509. Essa escolha permite avaliar como cada protocolo se comporta ao lidar com diferentes volumes de dados e operações de serialização.

Para viabilizar a observabilidade, o projeto integra Prometheus para coleta de métricas, Grafana para visualização e cAdvisor para monitoramento dos contêineres Docker. Essas ferramentas permitem acompanhar métricas como latência, uso de CPU e memória, e tamanho de payload em tempo real.

\section{AMBIENTE DE DESENVOLVIMENTO}\label{sec:ambiente}
% ----------------------------------------------------------

O ambiente de desenvolvimento foi configurado utilizando Go versão 1.24.6 como linguagem principal. A escolha do Go se justifica por suas características de performance, suporte nativo a concorrência através de \textit{goroutines} e amplo ecossistema para desenvolvimento de microsserviços. Além disso, a linguagem possui bibliotecas maduras tanto para construção de APIs REST quanto para implementação de serviços gRPC.

Para o desenvolvimento foi utilizado o \textit{goland} como editor principal. O projeto utiliza Go \textit{Modules} para gerenciamento de dependências, facilitando a reprodutibilidade do ambiente. As principais dependências incluem o framework gRPC (\texttt{google.golang.org/grpc}), Protocol Buffers (\texttt{google.golang.org/protobuf}), cliente Prometheus (\texttt{github.com/prometheus/client\_golang}) e geração de UUIDs (\texttt{github.com/google/uuid}).

A containerização foi realizada através do \textit{Docker}, permitindo que ambos os servidores executem em ambientes isolados e padronizados. O \textit{Docker Compose} orquestra os serviços necessários (REST, gRPC, \textit{Prometheus}, \textit{Grafana} e \textit{cAdvisor}), simplificando o processo de execução e testes.

\section{ESTRUTURA DO PROJETO}\label{sec:estrutura}
% ----------------------------------------------------------

A organização do código segue convenções da comunidade Go. O diretório \texttt{cmd/} contém os pontos de entrada das aplicações: \texttt{cmd/server/main.go} para o servidor REST e \texttt{cmd/grpc\_server/main.go} para o servidor gRPC. Esses arquivos são responsáveis apenas pela inicialização dos servidores e configuração básica.

A lógica de negócio reside no diretório \texttt{internal/}, que está dividido em camadas. A pasta \texttt{internal/domain/} contém as estruturas de dados do domínio, como \texttt{Certificate} e \texttt{CertificateRequest}. A camada \texttt{internal/service/} implementa a lógica de geração de certificados X.509, sendo compartilhada por ambas as implementações de protocolo.

Para REST, os controladores HTTP estão em \texttt{internal/api/controller/}, enquanto o middleware de métricas Prometheus fica em \texttt{internal/api/middleware/}. Para gRPC, a implementação do servidor está em \texttt{internal/grpc/server.go}. As definições Protocol Buffer residem em \texttt{proto/certificate.proto}, e o código Go gerado automaticamente pelo compilador protoc fica na mesma pasta.

Os arquivos de configuração Docker ficam em \texttt{zarf/docker/}, incluindo \texttt{rest.dockerfile} e \texttt{grpc.dockerfile}. O diretório \texttt{zarf/keys/} armazena as chaves RSA necessárias para assinatura de certificados, enquanto \texttt{zarf/certificates/} recebe os certificados gerados em tempo de execução.

\section{IMPLEMENTAÇÃO DOS SERVIDORES}\label{sec:servidores}

\subsection{Servidor REST}

O servidor REST foi implementado em \texttt{cmd/server/main.go} utilizando exclusivamente o pacote \texttt{net/http} da biblioteca padrão do Go, sem frameworks externos. O servidor escuta na porta 8000 e utiliza o multiplexador HTTP padrão para roteamento de requisições.

A inicialização do servidor segue uma estrutura de três camadas: serviços são instanciados primeiro (recebendo paths para chave privada e diretório de certificados), seguidos pelos controladores que dependem dos serviços, e finalmente as rotas HTTP são registradas. Esta arquitetura em camadas foi adotada para permitir reutilização da lógica de negócio entre o servidor REST e o servidor gRPC.

\begin{lstlisting}[language=Go, caption={Inicialização do servidor REST},label=lst:rest-init]
func main() {
    // Initialize services
    certificateService := service.NewCertificateService(
        "zarf/keys/private_key.pem",
        "zarf/certificates")

    // Initialize controllers
    certificateController := controller.NewCertificateController(
        certificateService)

    // Setup routes with Prometheus middleware
    http.HandleFunc("/certificate/all",
        middleware.PrometheusMiddleware(
            certificateController.GetAllCertificates))
    http.Handle("/metrics", promhttp.Handler())

    log.Fatal(http.ListenAndServe(":8000", nil))
}
\end{lstlisting}

Todos os \textit{endpoints} foram envolvidos pelo \texttt{PrometheusMiddleware} para coleta automática de métricas. O \textit{middleware} implementa três métricas principais: \texttt{http\_requests\_total} (contador de requisições por método, \textit{endpoint} e \textit{status}), \texttt{http\_request\_duration\_seconds} (histograma de latência com \textit{buckets} padrão do \textit{Prometheus}), e \texttt{active\_connections} (\textit{gauge} de conexões ativas). Esta instrumentação foi fundamental para as análises de desempenho apresentadas no Capítulo \ref{cap:resultados}.

\begin{lstlisting}[language=Go, caption={Middleware Prometheus implementado},label=lst:prom-middleware]
func PrometheusMiddleware(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        activeConnections.Inc()
        defer activeConnections.Dec()

        rw := &responseWriter{ResponseWriter: w, statusCode: http.StatusOK}
        next(rw, r)

        duration := time.Since(start).Seconds()
        httpRequestDuration.WithLabelValues(r.Method, r.URL.Path).Observe(duration)
        httpRequestsTotal.WithLabelValues(r.Method, r.URL.Path,
            strconv.Itoa(rw.statusCode)).Inc()
    }
}
\end{lstlisting}

Os endpoints implementados no servidor REST são:

\begin{itemize}
    \item \texttt{POST /certificate}: Gera um novo certificado X.509 baseado nos parâmetros recebidos em JSON
    \item \texttt{GET /certificate/get?filename=X}: Recupera um certificado específico por nome de arquivo
    \item \texttt{GET /certificate/list}: Lista os nomes de todos os certificados armazenados
    \item \texttt{GET /certificate/all}: Retorna um mapa completo com todos os certificados e seus conteúdos em formato JSON (endpoint principal utilizado nos testes de comparação)
    \item \texttt{GET /certificate/benchmark}: Endpoint de medição que retorna estatísticas de tempo de busca, serialização e tamanho do payload JSON
    \item \texttt{GET /metrics}: Expõe métricas do Prometheus para scraping
    \item \texttt{GET /health}: Verifica o status de saúde do serviço
\end{itemize}

O \textit{endpoint} \texttt{/certificate/all} foi escolhido como base de comparação por retornar o volume completo de dados, permitindo avaliar o comportamento dos protocolos sob carga de transferência significativa. A serialização de resposta é feita com \texttt{json.Marshal} da biblioteca padrão Go.

\subsection{Servidor gRPC}

O servidor gRPC foi implementado em \texttt{cmd/grpc\_server/main.go} escutando na porta 50051. O contrato de serviço foi definido utilizando Protocol Buffers versão 3 no arquivo \texttt{proto/certificate.proto}.

\begin{lstlisting}[caption={Definição do serviço em Protocol Buffers (certificate.proto)},label=lst:proto-def]
syntax = "proto3";
package certificate;

service CertificateService {
  rpc GetAllCertificates(GetAllRequest) returns (GetAllResponse);
  rpc ListCertificates(ListRequest) returns (ListResponse);
  rpc GetCertificate(GetRequest) returns (GetResponse);
  rpc BenchmarkGetAll(GetAllRequest) returns (BenchmarkResponse);
}

message GetAllResponse {
  map<string, string> certificates = 1;
}

message BenchmarkResponse {
  int32 certificate_count = 1;
  int64 payload_size_bytes = 2;
  double payload_size_mb = 3;
  int64 fetch_duration_ms = 4;
  int64 serialize_duration_ms = 5;
  int64 total_duration_ms = 6;
  string serialization_format = 7;
}
\end{lstlisting}

O método \texttt{GetAllCertificates} é equivalente ao endpoint REST \texttt{/certificate/all}, retornando um mapa de certificados. O método \texttt{BenchmarkGetAll} fornece estatísticas detalhadas de serialização Protobuf para comparação com JSON.

O código Go foi gerado automaticamente a partir do arquivo \texttt{.proto} usando os comandos:

\begin{lstlisting}[language=bash]
protoc --go_out=. --go_opt=paths=source_relative \
       --go-grpc_out=. --go-grpc_opt=paths=source_relative \
       proto/certificate.proto
\end{lstlisting}

A inicialização do servidor gRPC configurou \texttt{MaxRecvMsgSize} e \texttt{MaxSendMsgSize} para 50 MB, necessário porque a transferência de 15.110 certificados gera payloads próximos a 19 MB, superando o limite padrão de 4 MB do gRPC.

\begin{lstlisting}[language=Go, caption={Inicialização do servidor gRPC},label=lst:grpc-init]
func main() {
    certificateService := service.NewCertificateService(
        "/zarf/keys/private_key.pem",
        "/zarf/certificates")

    maxMsgSize := 50 * 1024 * 1024 // 50MB
    grpcServer := grpc.NewServer(
        grpc.MaxRecvMsgSize(maxMsgSize),
        grpc.MaxSendMsgSize(maxMsgSize),
    )

    certificateServer := grpcserver.NewCertificateServer(
        certificateService)
    pb.RegisterCertificateServiceServer(grpcServer, certificateServer)

    listener, err := net.Listen("tcp", ":50051")
    grpcServer.Serve(listener)
}
\end{lstlisting}

A implementação dos métodos RPC em \texttt{internal/grpc/server.go} delega a lógica de negócio para o mesmo \texttt{CertificateService} utilizado pelo servidor REST, garantindo comportamento idêntico entre os protocolos. A diferença reside exclusivamente na camada de transporte (HTTP/2 vs HTTP/1.1) e serialização (Protobuf vs JSON).

Cada método RPC foi implementado como uma função que recebe \texttt{context.Context} e uma mensagem de requisição, retornando uma mensagem de resposta e erro. Por exemplo, \texttt{GetAllCertificates} chama \texttt{certificateService.GetAllCertificates()}, recebe o mapa de certificados, e o encapsula em \texttt{pb.GetAllResponse\{Certificates: certificates\}}. O framework gRPC automaticamente serializa essa resposta em Protobuf binário antes de transmitir pela rede.

O método \texttt{BenchmarkGetAll} implementa medições detalhadas similares ao \textit{endpoint} REST equivalente. Ele mede o tempo de busca dos certificados, serializa manualmente a resposta usando \texttt{proto.Marshal} para obter o tamanho exato do \textit{payload} \textit{Protobuf}, e retorna estatísticas incluindo contagem de certificados, tamanho em \textit{bytes}, tempos de busca e serialização. Esta implementação foi essencial para comparar o desempenho de serialização entre JSON e Protobuf de forma controlada.

O servidor gRPC foi containerizado usando \textit{Dockerfile multi-stage} em \texttt{zarf/docker/grpc.dockerfile}. O primeiro estágio compila o código Go com \texttt{CGO\_ENABLED=0} para gerar binário estático, e o segundo estágio copia o binário para imagem \textit{Alpine Linux} mínima. Os volumes Docker mapeiam \texttt{zarf/keys} em modo read-only (fornecendo a chave privada RSA) e \texttt{zarf/certificates} em modo read-write (compartilhado com o servidor REST para armazenar certificados). Este compartilhamento de volumes garante que ambos os servidores acessem exatamente os mesmos arquivos de certificados durante os testes.

\section{LÓGICA DE NEGÓCIO COMPARTILHADA}\label{sec:logica}
% ----------------------------------------------------------

Ambos os servidores (REST e gRPC) compartilham a mesma implementação de lógica de negócio através do \texttt{CertificateService}, definido em \texttt{internal/service/certificate.go}. Esta decisão arquitetural foi fundamental para garantir que a comparação avalie exclusivamente as diferenças de protocolo e serialização, não diferenças na lógica de negócio.

A interface do serviço define quatro operações:

\begin{lstlisting}[language=Go, caption={Interface CertificateService},label=lst:cert-service-interface]
type CertificateService interface {
    GenerateCertificate(req domain.CertificateRequest) (*domain.Certificate, error)
    GetCertificate(filename string) (string, error)
    ListCertificates() ([]string, error)
    GetAllCertificates() (map[string]string, error)
}
\end{lstlisting}

O método \texttt{GetAllCertificates} é o mais relevante para os testes de comparação, pois retorna todos os certificados armazenados:

\begin{lstlisting}[language=Go, caption={Implementação de GetAllCertificates},label=lst:getall-impl]
func (s *certificateService) GetAllCertificates() (map[string]string, error) {
    files, err := filepath.Glob(filepath.Join(s.outputDir, "certificate_*.crt"))
    if err != nil {
        return nil, fmt.Errorf("failed to list certificates: %w", err)
    }

    certificates := make(map[string]string)
    for _, file := range files {
        filename := filepath.Base(file)
        certBytes, err := os.ReadFile(file)
        if err != nil {
            return nil, fmt.Errorf("failed to read certificate %s: %w", filename, err)
        }
        certificates[filename] = string(certBytes)
    }

    return certificates, nil
}
\end{lstlisting}

Este método busca todos os arquivos \texttt{.crt} no diretório configurado, lê cada arquivo e retorna um mapa onde a chave é o nome do arquivo e o valor é o conteúdo do certificado em formato PEM. Este mapa é então serializado em JSON (no servidor REST) ou Protobuf (no servidor gRPC).

A geração de certificados X.509 utiliza os pacotes \texttt{crypto/x509} e \texttt{crypto/rsa} da biblioteca padrão Go. Os certificados são autoassinados com chave RSA carregada de \texttt{zarf/keys/private\_key.pem}, têm validade de 1 ano, e incluem Conteúdo configurável. Cada certificado recebe número de série baseado no \textit{timestamp} Unix e é salvo com nome único incluindo timestamp e nanosegundos para evitar colisões.

\section{INTEGRAÇÃO COM OBSERVABILIDADE}\label{sec:observabilidade}
% ----------------------------------------------------------

A stack de observabilidade foi configurada usando Docker Compose com cinco serviços: rest-app, grpc-app, prometheus, grafana e cadvisor. O Prometheus coleta métricas de três fontes: endpoint \texttt{/metrics} do servidor REST (porta 8000), endpoint \texttt{/metrics} do servidor gRPC (porta 8000), e métricas de containers do cAdvisor (porta 8080).

A configuração do \textit{Prometheus} em \texttt{prometheus.yml} define intervalos de \textit{scraping} diferenciados:

\begin{lstlisting}[caption={Configuração do Prometheus (prometheus.yml)},label=lst:prometheus-config]
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'rest-app'
    static_configs:
      - targets: ['rest-app:8000']
    scrape_interval: 5s
    metrics_path: '/metrics'

  - job_name: 'grpc-app'
    static_configs:
      - targets: ['grpc-app:8000']
    scrape_interval: 5s
    metrics_path: '/metrics'

  - job_name: 'cadvisor'
    static_configs:
      - targets: ['cadvisor:8080']
    scrape_interval: 5s
    metrics_path: '/metrics'
\end{lstlisting}

Foi configurado scrape\_interval de 5 segundos para os servidores de aplicação (3x mais frequente que o padrão de 15s) para capturar picos de CPU e memória durante as transferências de certificados, que têm duração de poucos segundos. O Prometheus foi configurado com retenção de 200 horas (\texttt{--storage.tsdb.retention.time=200h}).

O cAdvisor foi configurado em \texttt{docker-compose.yaml} para coletar métricas de containers Docker com \texttt{housekeeping\_interval} de 10 segundos:

\begin{lstlisting}[caption={Configuração do cAdvisor (docker-compose.yaml)},label=lst:cadvisor-config]
cadvisor:
  image: gcr.io/cadvisor/cadvisor:latest
  ports:
    - "8080:8080"
  command:
    - --store_container_labels=true
    - --docker_only=true
    - --housekeeping_interval=10s
  volumes:
    - /:/rootfs:ro
    - /var/run:/var/run:ro
    - /sys:/sys:ro
    - /var/lib/docker/:/var/lib/docker:ro
  privileged: true
\end{lstlisting}

O \textit{Grafana} foi configurado com credenciais admin/admin e acessa os dados do \textit{Prometheus} para visualização. Os \textit{dashboards} criados exibem as métricas de CPU e memória coletadas pelo \textit{cAdvisor}, que são apresentadas nas Figuras \ref{fig:grafana-rest}, \ref{fig:grafana-grpc}, \ref{fig:grafana-rest-5k} e \ref{fig:grafana-grpc-5k}.

\section{METODOLOGIA DE COMPARAÇÃO}\label{sec:metodologia}
% ----------------------------------------------------------

Para viabilizar a comparação quantitativa entre REST e gRPC, foram implementados \textit{endpoints} especializados de \textit{benchmark} em ambos os servidores. Esses \textit{endpoints} executam operações idênticas: recuperam todos os certificados armazenados, serializam os dados e retornam métricas detalhadas sem transmitir o \textit{payload} completo pela rede.

O endpoint REST \texttt{/certificate/benchmark} mede o tempo de leitura dos arquivos do disco e o tempo de serialização JSON através de \texttt{json.Marshal}. O endpoint gRPC \texttt{BenchmarkGetAll} realiza medições equivalentes utilizando \texttt{proto.Marshal} para serialização Protobuf. Ambos retornam um objeto de resposta contendo:

\begin{itemize}
    \item Contagem de certificados processados
    \item Tamanho total do \textit{payload} em bytes e megabytes
    \item Tempo gasto na leitura do disco
    \item Tempo gasto na serialização
    \item Tempo total da operação
    \item Formato de serialização utilizado (JSON ou Protobuf)
\end{itemize}

\textit{Scripts} em \textit{shell} foram desenvolvidos para automatizar os testes de carga. O \textit{script} \texttt{compare.sh} executa requisições para ambos os \textit{endpoints} de \textit{benchmark}, extrai as métricas usando \texttt{jq} para \textit{parsing} JSON e calcula percentuais de redução de tamanho e ganhos de velocidade. Outro \textit{script}, \texttt{load\_test.sh}, permite executar múltiplas requisições concorrentes para simular carga e avaliar comportamento sob \textit{stress}.

\section{CONTAINERIZAÇÃO E ORQUESTRAÇÃO}\label{sec:containers}
% ----------------------------------------------------------

Os \textit{Dockerfiles} utilizam \textit{build} multi-estágio para otimizar o tamanho final das imagens. O primeiro estágio compila o código Go com \texttt{CGO\_ENABLED=0} para gerar binários estáticos que não dependem de bibliotecas C externas. O segundo estágio copia apenas o binário compilado para uma imagem Alpine Linux mínima.

Usuários não-root foram configurados nos contêineres por questões de segurança. Os volumes Docker mapeiam o diretório \texttt{zarf/keys} em modo read-only para fornecer as chaves de assinatura, e \texttt{zarf/certificates} em modo read-write para armazenar certificados gerados.

O \textit{Docker Compose} orquestra cinco serviços simultaneamente: \texttt{rest-app} na porta 8000, \texttt{grpc-app} na porta 50051, \texttt{prometheus} na porta 9090, \texttt{grafana} na porta 3000 com credenciais admin/admin, e \texttt{cadvisor} na porta 8080. Todos os serviços se comunicam através de uma rede \textit{bridge} padrão criada automaticamente.

\textit{Volumes} nomeados garantem a persistência de dados do \textit{Prometheus} e configurações do \textit{Grafana} mesmo após reinicialização dos contêineres.
